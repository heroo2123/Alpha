# V11 offline receipt-bundle preflight

Run `python -m polymarket_scanner.v11.receipt_bundle_preflight --manifest M.json --transaction T.json --receipt R.json --api-row A.json`. Every path is an explicit local regular file. The command prints one JSON object containing only sorted `diagnostics` codes and writes no files. It is independent of `inventory_shadow_start.py` and its accepted input and artifact contracts.

The manifest format is `{"version":"v11_receipt_bundle_preflight_v1","files":{...},"claim":{...}}`. `files` has exactly `transaction`, `receipt`, and `api_row`. Each entry has exactly `sha256` (lowercase SHA-256 of the entire named file) and `capture` (`captured_at_utc` in UTC seconds, nonempty `source`, nonempty `request_id`). Each saved file repeats that `capture` object. Transaction and receipt files contain a `response` JSON-RPC object with `jsonrpc:"2.0"`, the matching string `id`, and a `result` object. The API file contains `evidence_class:"API_OBSERVED"` and one `row` object. These capture labels are declarations inside caller-controlled bytes, not independent attestations.

`claim` has exactly `chain_id`, `block_number`, `block_hash`, `transaction_hash`, `transaction_index`, `receipt_status`, `log_index`, `log_address`, `log_topics`, `log_data`, `account`, `token_id`, `api_row_sha256`, `account_topic_index`, and `token_word_index`. Hashes and addresses use lowercase `0x` hex; RPC numeric fields use canonical hex quantities. `api_row_sha256` hashes the compact, sorted-key ASCII JSON encoding of `row`, without a trailing newline. The selected receipt log must match the claimed block, transaction, index, address, topics, data, and `removed:false`. The declared account topic must be a 32-byte padded account address, and the declared data word must equal the decimal token ID. Their positions are caller claims: without an independently reviewed ABI and event signature, agreement is only an internal consistency check.

All inputs have duplicate-key rejection, no-follow regular-file opens, 64 KB manifest and 256 KB per capture limits, a two-second per invocation deadline, nesting/node bounds, and at most 64 receipt logs. `SOURCE_ATTESTATION_MISSING` and `ABI_ATTESTATION_MISSING` are always present. A status other than exactly `0x1`, an RPC error, or any missing or conflicting identity adds further diagnostics. A response that merely looks successful is still an unverified receipt; the API row stays `API_OBSERVED`, and `SYNTHETIC_PROOF` is not consumed. The preflight has no acceptance or accounting output. Independent source provenance, deployed ABI/event semantics, pagination, opening inventory, basis, fees, and full transaction lineage remain for separate review.
