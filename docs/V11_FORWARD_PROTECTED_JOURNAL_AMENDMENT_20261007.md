## 3. Principal separation and corrected writer inventory

The review found runtime, author/reviewer agents, ledger files, request/snapshot inputs and the certification lock directory under `alphaadmin` uid 1000, which belongs to the sudo group. `SO_PEERCRED` distinguishes that uid from a future custodian uid; it cannot distinguish an AI agent from the runtime today. Sudo group membership is not evidence that arbitrary root commands are available, but any effective route from an untrusted uid to custodian/root privileges must be closed or excluded by the commissioning threat model. The same uid ambiguity applies to the owner-transition interface, not only to custodian/runtime separation: a bare peer-uid check cannot distinguish the owner from the runtime or an agent sharing uid 1000. The transition interface must therefore bind to an explicit principal distinguishable from uid 1000 — for example a root-only socket that accepts only peer uid 0, reachable only through a reviewed sudo rule naming the exact helper command, or an owner-held signing key never readable by uid 1000 — and no uid-1000 process may be treated as the owner regardless of sudo group membership, tty state or session sharing.

Sole-reader custody means only the custodian opens the physical database, including for checkpoint, backup, snapshot, qualification and status. It materializes a bounded immutable **logical** view from one pinned transaction and binds it to ledger and journal frontiers. The isolated verifier can read these exported bytes, not open an `immutable=1` copy as an independent ledger. View copies confer no identity; custody must authenticate every page/chunk, completeness declaration and frontier against the authoritative journal. Runtime may display the result but cannot mint it. A bug in the verifier can misclassify semantics, so independent review remains necessary; process isolation prevents that bug from rewriting custody evidence, not from returning a wrong answer.

Current `EvidenceStore` requires a private parent and owner-only DB mode; its constructor inspects existing metadata read-only before opening normal connections. Normal `_connect`, including reads and `pin_read_view`, opens RW and sets WAL pragmas. Existing runtime calls cannot simply continue after ownership changes. A future custodian adapter and isolated semantic verifier must replace those calls for enrolled ledgers. No permission migration of an old ledger can retrospectively establish custody.

## 4. Identity, rotation and the disclosure window

Enrollment assigns a non-reused custodian-generated `ledger_id` and genesis commitment, independently of namespace/path/inode. Future metadata must bind that ID in `v11_meta`, the journal enrollment, every operation, every head guard, every exported view and every seal. Head identity is `(ledger_id, kind, event_id, seq, body_sha256)`; a full frontier also binds the authenticated prefix digest. Bare seq equality is insufficient.

For proposed version 1, rotation closes admission, terminally aborts open operations, freezes the **whole** old ledger with its complete prefix and sidecar/checkpoint state, and seals an archive manifest. Checkpoint and archive operations belong to the custodian; no other connection or inherited descriptor may be live. A failed or ambiguous checkpoint, rename or directory sync leaves the domain closed. It must never discard the suffix after a review frontier. A successor gets a new ID/genesis and no copied rows, capability proofs, admission, children or capture. Its certification proofs must be re-minted for the new ledger. An archive catalog may order predecessor/successor identities for retention and completeness; it does not make them one ledger or transfer qualification.

All plan/admission/source/features/decisions/capture/raw receipts/labels/qualification dependencies for a sample must remain in its original ledger ID. No interval crosses rotation, and no sample pending labels is completed using the successor. If rotation is necessary while the capture-to-qualification window is open, that sample is UNKNOWN. Old sealed ledgers can be re-verified only as complete independent ledgers; missing required archived bytes means refusal. A manifest of segments is not permission to splice rows from different IDs. Later relevant conflicts or invalidations still remove credit; sealing an archive does not prove that no external disclosure can ever occur.

Positive lineage is single-ledger, but refusal is not: a missing early disclosure must not become invisible merely because it was recorded before a rotation or routed to a different enrolled ledger ID. The custodian must maintain, and the verifier must consult, an authenticated catalog of every predecessor and sibling enrolled ledger it holds for the same namespace, plan or event — including that ledger's same-event raw receipts, labels, invalidations, prior admissions and qualifications — before any positive result for that event. A catalog member that cannot be located, opened or authenticated produces refusal, not a pass; callers who route a receipt for the same event to a different enrolled ledger ID do not thereby remove it from the refusal check. Equivalently, enrollment may instead forbid admitting any event that already has a record in a predecessor or sibling enrolled ledger; either rule closes this gap, and a future implementation review must pick one. Status aggregation across plan targets must be computed over the union of a plan's enrolled ledgers, deduplicated by event ID and grouped-outcome ID, so the same event is never counted once per ledger.

The important rollback window extends from original admission/capture through raw/label collection, qualification and the frontier used by each later status. Restoring a valid old prefix that omits an early `GAMMA_CLOSED_MARKET` receipt, duplicate LABEL or proof invalidation can hide a refusal even when the capture seal itself survives. Thus anchoring only the capture interval is insufficient. A status result is tied to its authenticated current frontier, not permanently valid because a receipt once existed.

The review found no `/dev/tpm*`, an empty TPM class, and one ext4 `/` containing ledger, journal and root state; network transport is excluded. No durable independent anchor is established. Version 1 therefore makes every dependent sample UNKNOWN after an unanchored custodian restart/reboot/instance replacement, even if it had a complete capture seal or a qualification receipt. Hashes, boot IDs, generations or restored local checkpoints cannot repair this. Fresh enrollment/session may start future work after custody reconciliation; it never repairs old samples.

A future same-session claim would require separately commissioned exclusive custody and a live custodian-held high-water commitment covering **all** evidence and journal entries, including disclosure and invalidation, from enrollment to the present snapshot. No such session or anchor exists in this proposal. The pure offline interface must reject missing commissioned anchor input with `ANCHOR_UNAVAILABLE`, even if every hash otherwise matches. To support cross-session claims later would require a new reviewed anchor design, for example an owner-held out-of-band head that commits both frontiers and is advanced for every relevant durable change before it can be forgotten, then re-attested on restart. A once-per-session start checkpoint is insufficient. A custodian's in-session high-water commitment, including the one added in §5 for its own storage witnessing, is not itself a commissioned anchor and may not be passed as the `anchor` argument to the offline verifier without its own separately reviewed design; conflating the two would let an implementer treat an in-memory head as satisfying anchor availability. Remote witnesses require a separately reviewed network exception and are outside version 1.

## 5. Proposed custody state machine, witnesses and lock order

These are protocol requirements for review, not callable APIs. Strict versioned envelopes must reject unknown authority fields, duplicate keys, wrong types, nonfinite times, excessive sizes and unsupported versions. Minimum bindings are: custodian executable/policy identity, journal ID/contiguous seq/previous hash, session and boot ID, ledger ID/genesis/frontier, interval and operation IDs, exact opaque row digest, protected dependency identities and retained-byte digests, witness tuple, clock bracket and reason. Every envelope states `financial_authority=False`. A locator or custody seal never states that the semantic predicates passed.

**Lock order:** acquire the single bounded domain fence `C` first; then any owner publisher slot lock `A` (only for a transition); then ledger transaction `L` (only for ledger operations); then journal append critical section `J`. In symbols, `C -> A (if needed) -> L (if needed) -> J`. `A` and `L` are not needed together in the version-1 transition flow. Journal append and fsync may occur before starting `L`, but `J` must be released before acquiring `L`; no nested acquisition reverses the order. No caller holding an old publisher/role/SQLite lock may enter `C`. The sole journal writer normally makes `J` an internal serialization step, not another externally selectable lock. Release in reverse order. Deadlines, work/byte limits and revocation queue priority must be frozen in a later reviewed policy; an unset or exceeded bound disables enrollment/publication.

`C` must be a new fixed lock inode in a root-provisioned directory outside runtime-writable parents, with boot-time creation by root before clients start, safe descriptor opening, owner/mode/device/inode checks, close-on-exec, no descriptor inheritance and bounded acquisition. A concrete proposed location is `/run/alpha-v11-forward-custodian/publication.lock`, distinct from `/var/lock/alpha-v11`. Root controls its creation/replacement; the custodian holds it for every normal operation, including owner-requested transitions. Root maintenance may acquire it only after ending the session and stopping admission. Losing identity or custody ends the session. This path is a proposal, not a claim that it exists.

The fence orders cooperative writers. To detect ordinary unmediated changes, the custodian also collects witnesses for every protected dependency and its parent directories, at opening, immediately before PREPARE, immediately after evidence commit, before final seal, and at every subsequent boundary. The set includes the whole certification manifest, exact model state, approved manifests/policies/objects, the protected executable/configuration dependencies fixed at enrollment, and the custodian's **own** enrolled ledger DB/WAL/SHM, journal and archive files and their parent directories — the custodian's own storage is witnessed, not assumed stable merely because the custodian opened it. Compare each observation with the **last accepted observation**, including between child operations, and against the **in-memory session high-water** the custodian holds for that storage, not only against bytes read back from disk; comparing only pre/post within one append would miss a between-children change, and comparing only on-disk state would miss a same-session swap that a reopen-by-path would silently follow.

Each witness binds `st_dev`, `st_ino`, ext4 inode generation (`FS_IOC_GETVERSION`), `st_ctime_ns`, `st_mtime_ns`, size, regular-file SHA-256, owner/mode/link constraints and relevant `/proc/self/mountinfo` lines. Parent directories get identity/change metadata and the bound child relation, not a claim that directories can be read as regular file bytes. Use safe pinned descriptors, stat-before/hash/stat-after and parent/path rechecks; unstable collection, unsupported generation, missing component, unexpected mount, symlink/hardlink or mixed bytes is UNKNOWN. Retain immutable copies of the exact manifest/model/object bytes for the semantic verifier; a hash without retrievable bytes is insufficient.

This explicitly proposes the review's kernel-witness mechanism, rather than relying on content endpoint equality. Replace-and-restore, same-content replacement, rewrite followed by `utime` reset, and rename-away/back should change inode/generation/ctime or parent witnesses and abort. It is **not** an unconditional detector for all histories: mount overlay/removal entirely between samples, same-inode same-tick rewrites restored to identical content, or privileged timestamp/metadata manipulation may evade endpoint tuples. Generation/hash do not automatically fix every such ABA. Owner commissioning must exclude uncontrolled writers/mount/clock/restore operations during coverage and an independent review must establish the supported filesystem guarantees. Where those guarantees cannot be established, coverage is UNKNOWN. A file watcher and frequent polling are not substitutes for custody. Bracketing alone grants no positive credit.

During a transition the custodian retains `C`; the root helper cannot re-enter `C`, request a ledger connection or call a service operation that waits on `C`. Its one-use authorization binds the transition ID, exact protected paths and permitted action, never arbitrary candidate code or shell commands. Helper timeout or lost acknowledgement leaves the transition unresolved and domain closed until the helper is fenced out and the owner reconciles it; late writes cannot race a reopened domain. Provider I/O and expensive inference are outside these critical sections.

Opening and append APIs from the original memo are therefore custody operations, not calls to candidate admission code inside a privileged daemon. A future semantic layer must re-derive **all** original `StrategyAdmission`, certification, model, safety-append and guardian constraints over the pinned view. The original admission assessment must be reconstructible at the OPEN snapshot/time, before original admission commit; a worker assessment made earlier is not proof of eligibility at OPEN. Existing pre-append runtime checks are not removed by this proposal. The minimal privileged storage protocol and its relation to those checks need separate design/implementation review before any runtime integration; opaque storage alone does not preserve all current runtime semantics.

An operation SEAL may cover only newly committed rows with seq strictly above its interval's opening frontier, PREPARE and SEAL in that same interval/session/ledger ID, and exact original payload bindings. `_append` currently returns existing rows before CAS/guardian/clock checks, while deterministic capture child IDs permit replay. Such a return must never create PREPARE or SEAL or attach the row to another interval. After abort, use a fresh original admission/interval and capture `record_id` with fresh child IDs. After a lost acknowledgement for an already durably sealed operation, the custodian may return the identical authenticated seal after current proof checks, with no new time, row or count. An unsealed old row cannot be repaired by retry.

Queued revocations may not be overtaken by new publications. A publication already in its bounded section can finish before a cooperative revocation; the owner acknowledgement must name the real effective journal point, never a backdated time. Emergency actions outside the protocol invalidate overlapping coverage. A later ordinary revocation need not erase an already proven historical capture, but custody compromise, hidden evidence or missing disclosure continuity does invalidate reliance on it.

## 6. Time, snapshots and resource failure

The proposed trusted clock binds `CLOCK_BOOTTIME` to `/proc/sys/kernel/random/boot_id` and a unique custodian process session; `CLOCK_MONOTONIC` alone omits suspend time. Sample UTC/error metadata from read-only `adjtimex` (`maxerror`, `esterror`, `STA_UNSYNC`) at both ends of each bracket and monitor wall steps with `timerfd` `TFD_TIMER_CANCEL_ON_SET`. A later review must fix units, conservative error calculation, sampling latency and maximum permitted uncertainty. Those kernel estimates are inputs requiring reviewed trust assumptions, not an automatic proof of UTC accuracy. Reported `NTPSynchronized=yes` is only an observation.

Require the whole original-assessment-to-final-seal span to fit the exact admission, source, rule, certification and applicable capture/decision leases. Against a foreign UTC expiry require `bracket_upper + error < expires_at`; also respect the lower eligibility boundary with its uncertainty. Equality/overlap refuses. Final capture commit/seal upper bound must strictly precede the earliest same-event recorded disclosure lower bound. Injectable `store.clock()`, body `recorded_at`, publisher pre-lock `time.time()` and status `as_of` cannot substitute for commit time. Wall steps, regression, cancellation-monitor failure, suspend crossing a deadline, unknown mapping and cross-boot comparisons refuse; never clamp or backdate.

Qualification and status use one pinned custodian read transaction, not independently paginated connections. A view binds `(ledger_id, seq, prefix_hash)` and `(journal_id, generation, seq, head_hash)` with all relevant archives/invalidation history. The isolated verifier consumes that immutable bounded view. The verifier's returned verdict must itself bind the exact view digest, this frontier pair, the verifier executable/policy identity and the request ID; the custodian authenticates the verdict's peer identity and rejects any verdict that fails to bind all four, or that binds a different view or frontier pair, before treating it as input to CAS — such a verdict is refused, not treated as a cache miss. Before persisting any future qualification receipt, reacquire `C`, validate the complete current frontier pair, and CAS it in the transaction; any raw receipt, duplicate label, other evidence or invalidation arriving during verification forces re-verification. The receipt binds the pre-receipt verified frontiers plus its own append seal, avoiding self-referential frontier claims. Status re-verifies against a fresh pair and trusted time; cached receipts, counts and earlier success responses grant no authority.

Preserve original plan-before-admission, original admission reference, MODEL-before-inference, FEATURES-before-DECISION, all decisions-before-capture, exact partition/token and one-winner rules, unchanged head checks, feature/release/scope/rule/model bindings and lease bounds. Scan every same-event raw receipt, including unselected/roleless recaptures; malformed, duplicate or conflicting labels and incomplete histories refuse. Retain current LABEL (1,000), raw RULES (10,000) and admission/guard (10,000) coverage limits as refusal boundaries, never as permission to trim. Admission IDs and grouped-outcome IDs must independently meet the plan target. `independent_label_attestation=False` remains: local receipt ordering proves neither provider-global earliest knowability nor absence of prior human/model exposure or economic validity.

The shared ext4 failure domain and the ledger's 64 MiB minimum-free setting do not reserve journal capacity. Commissioning must preallocate and test a separate journal emergency reserve for bounded SEAL/ABORT/GAP records, with admission stopped before consuming it; reserve sizing must cover outstanding operations and recovery overhead. ENOSPC, short writes, fsync/directory-sync failure, busy/timeout or exhausted verification bounds close publication. If the reserve also fails, unresolved records remain UNKNOWN on recovery. No numeric safe capacity or liveness is asserted here.

F10 liveness remains a separate go/no-go input: the reported per-minute cron can attempt whole-manifest publication (not necessarily replace bytes every tick), review TTL is 259200 seconds, rollover threshold is 220 MiB, and model epoch is capped at 1000. Review filenames show observer rotations on successive days with maxima 32726, 29074 and 29197; these demonstrate seq reuse, not a measured interval distribution. Restart frequency and actual manifest-change timestamps are not established here. A retained-metadata estimate must compare uninterrupted custody/manifest/ledger windows with capture-to-label latency, without treating missing periods as healthy. Until those inputs exist, attainable sample throughput is UNKNOWN and could be zero. Per-scope manifests or rotation-free label windows may need separate design; no limit is relaxed to improve liveness.
